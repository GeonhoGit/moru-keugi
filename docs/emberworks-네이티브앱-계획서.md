# Emberworks 네이티브 앱 전환 계획서

> 문서 목적: React 웹 프로토타입을 iOS App Store / Google Play Store에 출시 가능한 네이티브 클릭커 게임으로 전환하기 위한 개발 기준서
>
> 핵심 원칙: **기능 수보다 저장 안정성·밸런스·첫 플레이 경험을 우선하고, 수익화와 온라인 기능은 실제 리텐션을 확인한 뒤 단계적으로 도입한다.**

---

## 1. 프로젝트 개요

- **현재 상태**: 대장간 콘셉트의 클릭커 게임, React 웹 프로토타입 완성
- **최종 목표**: iOS App Store와 Google Play Store에 정식 출시 가능한 네이티브 앱으로 전환
- **1차 출시 목표**: 결제나 서버 없이도 완결된 핵심 플레이 루프를 제공하는 안정적인 V1.0 출시
- **핵심 플레이 감정**: 낡은 대장간이 플레이와 함께 시각적·청각적으로 성장하며, 짧은 직접 플레이와 장시간 방치 플레이가 모두 보상받는 경험

### 1.1 제품 원칙

1. 첫 30초 안에 타격, 재화 획득, 첫 업그레이드의 재미를 경험하게 한다.
2. 앱 종료·강제 종료·업데이트 이후에도 진행 데이터를 안전하게 보존한다.
3. 광고와 결제는 핵심 루프를 방해하지 않으며, 경쟁 콘텐츠의 공정성을 훼손하지 않는다.
4. 새로운 시스템은 별도 재화를 무작정 추가하기보다 대장간 세계관과 기존 재화를 활용한다.
5. 계산 로직, 데이터, 화면, 저장소를 분리해 밸런스 수정과 테스트가 쉽도록 만든다.

### 1.2 V1.0 성공 기준

- 튜토리얼을 마치면 플레이어가 타격·자동 생산·업그레이드·주문 제작·환생의 관계를 이해할 수 있다.
- 앱을 강제 종료하거나 백그라운드로 전환해도 저장 데이터가 손상되지 않는다.
- 첫 세션 15~20분 동안 최소 3회의 의미 있는 성장 연출이 발생한다.
- 첫 환생이 지나치게 빠르거나 느리지 않고 목표 범위인 1~2일 안에 가능하다.
- 광고·결제·계정 없이도 게임의 핵심 진행이 완결된다.
- 주요 화면이 저사양 Android 기기와 노치가 있는 iPhone에서 안정적으로 동작한다.

## 2. 버전 범위 및 출시 전략

모든 기능을 한 번에 개발하지 않고, 아래와 같이 버전별로 분리합니다.

| 버전 | 핵심 목표 | 포함 기능 |
|---|---|---|
| **V1.0 핵심 출시** | 저장 안정성과 핵심 재미 검증 | 타격, 자동 생산, 일반 업그레이드 8~12종, 구매 수량 1/10/최대, 업적 10~15개, 기본 주문 제작, 오프라인 보상, 첫 환생, 튜토리얼, 설정, 접근성, 대장간 시각 성장 |
| **V1.1 리텐션 업데이트** | 재방문과 수집 동기 강화 | 일일 주문, 주간 목표, 유물 15종+보상 유물 4종, 도감, 선택형 보상 광고, 확장 업적 |
| **V1.2 온라인 업데이트** | 계정·공정 경쟁·구매 기반 마련 | 계정, 클라우드 저장, 동일 조건 챌린지 랭킹, 친구 비교, 구매 검증 서버, 선택적 룬 파편 도입 |
| **V2.0 장기 콘텐츠** | 수개월 단위 진행 확장 | 신규 대장간 월드, 2차 환생, 시즌 이벤트, 시즌 패스, 고급 커스터마이징 |

### 2.1 V1.0에서 제외하는 기능

개발량과 운영 위험이 크므로 첫 출시에서 제외합니다.

- 유물 뽑기 및 유물 도감
- 룬 파편 판매와 소비성 인앱 결제
- 실시간 또는 글로벌 리더보드
- 시즌 패스
- 2차 환생
- 신규 월드
- 강제 전면 광고
- 계정 및 클라우드 저장

### 2.2 출시 전략

- V1.0은 **싱글 플레이·로컬 저장·비결제 버전**으로 완성도를 검증합니다.
- 앱스토어 계정 생성과 테스트 트랙 준비는 개발 후반이 아니라 Phase 0부터 병행합니다.
- 스토어와 계정 유형에 따라 별도 비공개 테스트 요건이 적용될 수 있으므로, 출시 직전에 각 콘솔의 최신 요구사항을 확인합니다.
- V1.1 이후 기능은 D1·D7 재방문율, 첫 환생 도달률, 크래시 없는 세션 비율을 확인한 뒤 도입합니다.

## 3. 기술 스택 및 아키텍처

### 3.1 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 앱 프레임워크 | **React Native + Expo** | 기존 React 로직 재사용, iOS·Android 단일 코드베이스, EAS Build로 Mac 없이도 iOS 빌드 가능 |
| 언어 | TypeScript | 게임 데이터와 저장 스키마의 타입 안정성 확보 |
| 빌드 | EAS Build | 로컬 환경 차이를 줄이고 iOS·Android 빌드 관리 |
| 내비게이션 | Expo Router 또는 React Navigation | 화면 구조와 딥링크를 일관되게 관리 |
| 상태 관리 | 가벼운 전역 상태 저장소 + 순수 게임 엔진 | 렌더링 상태와 게임 계산 분리 |
| 로컬 저장 | V1.0은 AsyncStorage 기반 저장 어댑터 | 단일 플레이어 저장 구조에 충분, 구현 범위가 작음 |
| 장기 저장 확장 | 필요 시 SQLite 또는 클라우드 저장소로 교체 | 데이터 규모와 온라인 기능 증가에 대비 |
| 분석 | 이벤트 추상화 계층부터 구현 | 분석 공급자를 바꾸더라도 게임 코드 수정 최소화 |

### 3.2 Expo 사용 원칙

- Expo Go는 초기 UI 확인에만 사용합니다.
- 햅틱, 알림, 광고, 결제 등 네이티브 모듈 검증은 **Development Build와 실제 기기**에서 진행합니다.
- 개발 환경을 `development`(로컬 개발·디버그) / `preview`(내부 QA·비공개 테스터) / `production`(스토어 제출·운영)으로 분리합니다.

### 3.3 권장 폴더 구조

```text
src/
├─ engine/          # 순수 게임 계산 로직 (economy/upgrades/prestige/offline)
├─ data/            # 업그레이드·업적·주문·유물 설정값
├─ state/           # 현재 플레이 상태 및 화면 상태
├─ storage/         # 저장, 백업, 검증, 마이그레이션
├─ services/        # 사운드, 햅틱, 분석, 광고, 결제, 알림
├─ screens/         # 주요 화면
├─ components/      # 공통 UI
├─ hooks/
├─ utils/
└─ types/
```

### 3.4 구현 원칙

- 생산량, 비용, 환생 보상, 오프라인 보상은 React 컴포넌트 안에서 계산하지 않습니다. `engine/`의 계산 함수는 입력을 받아 결과만 반환하는 순수 함수로 작성합니다.
- 업그레이드 수치와 해금 조건은 코드에 흩어놓지 않고 `data/`의 설정값으로 관리합니다.
- 저장소 접근은 `storage/` 어댑터를 통해서만 하며 화면이 AsyncStorage를 직접 호출하지 않게 합니다.
- 광고·결제·분석은 인터페이스를 먼저 만들고 V1.0에서는 비활성 구현체를 사용합니다.
- **큰 수 처리**: 5번 섹션의 비용·생산 공식은 개념 표기이며, 실제 구현에서는 이 값들을 일반 `number`가 아니라 문자열 직렬화를 지원하는 큰 수(BigNumber) 라이브러리의 곱셈·나눗셈·거듭제곱 API로 옮겨 작성합니다. 공식 문서와 실제 구현 사이의 이 변환 지점을 Phase 1에서 명시적으로 검증합니다.

## 4. 핵심 플레이 및 콘텐츠 기획

### 4.1 핵심 루프

```text
모루 타격 → 잉걸불 획득 → 업그레이드 구매 → 타격력·자동 생산 증가
→ 주문 제작 완료 → 대장간 시각 성장 → 진행 정체 시 환생 → 영구 능력 강화 후 재도전
```

### 4.2 V1.0 필수 콘텐츠

| 콘텐츠 | 설명 | 우선순위 |
|---|---|---|
| 모루 타격 | 직접 입력에 즉각적인 사운드·햅틱·숫자 피드백 제공 | 필수 |
| 자동 생산 | 업그레이드를 통해 초당 잉걸불 생산 | 필수 |
| 업그레이드 | 자동 생산형·타격형·배율형으로 성장 선택 제공 | 필수 |
| 기본 주문 제작 | 생산량을 소비해 무기 주문을 완성하고 보상 획득 | 필수 |
| 업적 | 누적 잉걸불, 타격 수, 업그레이드 보유 수 등 장기 목표 | 필수 |
| 오프라인 복귀 | 앱을 떠난 동안 생산된 잉걸불을 복귀 화면에서 지급 | 필수 |
| 환생 | 현재 진행을 초기화하고 영구 성장 재화 획득 | 필수 |
| 대장간 성장 연출 | 화로·모루·배경·음악이 누적 진행에 따라 변화 | 필수 |
| 튜토리얼 | 타격 → 첫 업그레이드 → 첫 자동 생산 → 첫 주문 순서 안내 | 필수 |

### 4.3 주문 제작 시스템

"오늘 500번 타격하기" 같은 범용 퀘스트 대신, 대장간 세계관과 직접 연결되는 단기 목표입니다. 룬 파편이 V1.2로 미뤄진 만큼, V1.0에서는 무과금 유저의 주 재방문 동기를 이 시스템이 담당합니다.

**V1.0 기본 구조**
- 주문은 3개 슬롯을 사용하며, 각 주문은 필요한 잉걸불·해금 조건·보상을 가집니다.
- "제작 시작"을 눌렀을 때만 진행이 시작되고, 필요 잉걸불은 즉시 차감하거나 생산량이 자동 투입되게 할 수 있습니다.
- V1.0은 서버 시간 없이도 동작하도록 고정 주문 목록을 순환합니다.
- 보상은 잉걸불, 명인의 인장 진행 보너스, 외형 해금, 업적 진행도로 구성합니다.

| 주문 | 조건 | 필요량 | 보상 |
|---|---|---:|---|
| 농부의 낫 | 시작부터 | 500 잉걸불 | 200 잉걸불 + 도감 기록 |
| 경비대의 철검 | 자동 생산 10/초 이상 | 5,000 잉걸불 | 1,500 잉걸불 + 타격력 임시 강화 |
| 광산용 곡괭이 | 중급 업그레이드 해금 | 25,000 잉걸불 | 업적 진행 + 대장간 장식 |
| 불꽃 룬 대검 | 첫 환생 이후 | 250,000 잉걸불 | 명인의 인장 진행 보너스 |

**V1.1 확장**: 일일 주문 3개, 주간 대형 주문 1개, 미완료 주문 교체 기능, 유물 조각·외형 아이템·보상형 광고 보너스 연결

### 4.4 대장간 시각적 성장

숫자만 증가하는 느낌을 줄이기 위해 아래 요소를 누적 잉걸불과 업적에 따라 변경합니다.

- 낡은 오두막 → 석조 대장간 → 왕실 대장간 → 용의 대장간
- 모루 외형과 타격 이펙트 / 화로 불꽃 크기와 색상
- 배경 NPC와 제작 중인 무기 / 파티클 수와 조명 강도
- BGM 악기 구성과 웅장함

### 4.5 선택 콘텐츠: 열기와 완벽 타격

V1.0 핵심 안정화 후 실험합니다. 연속 타격으로 열기가 상승하고, 특정 구간에서 완벽 타격 확률이 증가하며, 멈추면 열기가 서서히 감소합니다. 방치 플레이어가 손해를 보지 않도록 직접 플레이의 짧은 보너스로만 사용합니다.

### 4.6 아트 스타일 가이드

**전체 방향**
- 톤: 아늑하면서도 점점 웅장해지는 성장형 판타지 대장간. 초반은 소박하고 손때 묻은 느낌, 후반은 화려하고 신비로운 느낌으로 대비를 줍니다.
- 스타일: **도트(픽셀 아트)**를 채택합니다. 방치·클릭커 장르에서 관습적으로 익숙한 스타일이고, 업그레이드·업적·유물처럼 수량이 많은 소형 아이콘을 그리드 기준으로 일관되게 대량 제작하기 유리하며, 프리랜서 수급과 상용 에셋 팩 확보도 벡터 일러스트보다 수월합니다. 파일 용량이 작아 앱 크기 관리에도 유리합니다.
- 라인: 1px 단위 외곽선과 제한된 팔레트로 형태를 구분합니다.

**해상도 및 스케일 규칙**
- 원본 그리드 기준을 정합니다: 오브젝트·캐릭터 32×32px, 아이콘 16×16px 또는 24×24px, 배경은 별도 기준 해상도(예: 320×180)로 통일
- 고밀도 화면에서 흐려지지 않도록 **정수 배율(1x/2x/3x/4x)** 로만 확대·축소합니다. 1.5x 같은 소수 배율은 사용하지 않습니다.
- 렌더링 시 nearest-neighbor(최근접 이웃) 스케일링을 적용해 도트 경계가 부드럽게 뭉개지지 않도록 합니다. React Native에서의 실제 처리 방식은 Phase 4(네이티브 UX)에서 실기기로 검증합니다.

## 5. 업그레이드 설계

### 5.1 업그레이드 유형

| 유형 | 설명 | 예시 |
|---|---|---|
| 자동 생산형 | 초당 잉걸불 생산량 증가 | 견습 대장장이, 풀무, 석탄 화로 |
| 타격력형 | 한 번 타격 시 획득량 증가 | 무쇠 집게, 룬 각인 망치 |
| 배율형 | 특정 생산 계층에 배율 적용 | 명장의 모루, 용염의 화로 |
| 편의형 | 직접 생산량 대신 UX·오프라인 효율 개선 | 오프라인 효율, 주문 슬롯 강화 |

> 룬 파편 전용 업그레이드는 V1.0에서 제외하고 V1.2 이후 검토합니다.

### 5.2 업그레이드 데이터 구조

```ts
interface UpgradeDefinition {
  id: string;
  name: string;
  description: string;
  type: 'auto' | 'click' | 'multiplier' | 'utility';
  baseCost: string;       // 큰 수 라이브러리 문자열
  costGrowth: number;
  baseOutput: string;     // 큰 수 라이브러리 문자열
  unlockCondition: UnlockCondition;
  milestoneBonuses: MilestoneBonus[];
  maxLevel?: number;
}
```

### 5.3 티어 구조 및 해금 조건

| 티어 | 포함 업그레이드 | 해금 조건 |
|---|---|---|
| 초급 | 견습 대장장이, 무쇠 집게 | 게임 시작부터 |
| 중급 | 풀무, 석탄 화로 | 초급 업그레이드 각각 1개 이상 |
| 고급 | 룬 각인 망치, 명장의 모루 | 중급 업그레이드 각각 3개 이상 |
| 전설 | 용염의 화로, 명인의 설계도 | 첫 환생 완료 |

### 5.4 비용 공식

```text
다음 1개 비용 = floor(기본가 × 성장률^보유개수)      기본 성장률 = 1.15
N개 총비용 = 기본가 × 성장률^보유개수 × (성장률^N - 1) ÷ (성장률 - 1)
```

- 화면에 `[1개] [10개] [최대]` 구매 옵션을 제공합니다.
- 최대 구매는 반복문 대신 수식 또는 이진 탐색으로 계산합니다.
- 가격 표시 반올림 규칙을 통일합니다.

### 5.5 생산 공식

```text
업그레이드 생산량 = 기본 생산량 × 보유개수 × 마일스톤 배율
기본 자동 생산량 = Σ(각 업그레이드 생산량)

최종 자동 생산량 = 기본 자동 생산량 × 자동 생산 배율 × 전체 생산 배율 × 환생 배율
최종 타격량     = (기본 타격량 + 업그레이드 추가 타격량) × 타격 배율 × 전체 생산 배율 × 환생 배율
```

(배율 항목의 정의와 스택 규칙은 6.3 참고)

### 5.6 마일스톤 보너스

업그레이드 10·25·50·100개 보유 시 배율 보너스를 제공합니다. (예: 10개 ×2, 25개 ×2, 50개 ×3, 100개 ×4 — 실제 배율은 스프레드시트 시뮬레이션으로 조정)

### 5.7 상점 UI 필수 정보

현재 보유 수, 현재 생산 기여량, 구매 후 증가량·증가율, 구매 가격, 구매 가능까지 예상 시간, 다음 마일스톤까지 남은 수량을 표시합니다.

```text
견습 대장장이 Lv.24
현재: +125 잉걸불/초 → 구매 후: +132 잉걸불/초 (+5.6%)
다음 25레벨 보너스: 생산량 ×2 / 구매 가능까지: 약 18초
```

## 6. 밸런스 및 환생 설계

### 6.1 화로 티어

환생 후에도 유지되는 평생 누적 잉걸불을 기준으로 판정합니다.

| 티어 | 이름 | 누적 잉걸불 기준 | 연출 |
|---|---|---:|---|
| 0 | 초심자의 화로 | 0 이상 | 주황 불꽃, 낡은 오두막 |
| 1 | 타오르는 화로 | 300 이상 | 진한 주황, 화로 크기 증가 |
| 2 | 작열하는 용광로 | 8,000 이상 | 금빛 불꽃, 석조 대장간 |
| 3 | 용염의 성화 | 200,000 이상 | 하늘빛 백광, 왕실 장식 |

수치는 초기 기준이며 실제 플레이 테스트 후 조정합니다.

### 6.2 진행 페이싱 목표

| 마일스톤 | 목표 도달 시점 |
|---|---|
| 첫 업그레이드 구매 | 시작 후 약 10초 |
| 첫 자동 생산 획득 | 약 30초 |
| 첫 주문 완료 | 약 2~4분 |
| 첫 화로 티어 변화 | 약 5분 |
| 초·중급 업그레이드 모두 보유 | 첫 세션 15~20분 내 |
| 환생 메뉴 해금 | 첫날 후반 |
| 첫 환생 가능 | 1~2일차 |
| 두 번째 환생 | 3~5일차 |

### 6.3 보너스 스택 규칙

같은 계층의 퍼센트 보너스는 먼저 더하고, 서로 다른 계층은 곱합니다. 생산·타격 외에 **주문 보상**과 **오프라인 효율**도 유물·인장 강화에서 등장하는 별도 계층이므로 동일한 규칙으로 명시합니다.

```text
전체 생산 배율   = 1 + 전체 생산 보너스 합계
자동 생산 배율   = 1 + 자동 생산 보너스 합계
타격 배율        = 1 + 타격 보너스 합계
주문 보상 배율   = 1 + 주문 보상 보너스 합계
오프라인 효율 배율 = 1 + 오프라인 효율 보너스 합계
```

```text
최종 자동 생산량 = 기본 자동 생산량 × 자동 생산 배율 × 전체 생산 배율 × 환생 배율
최종 타격량      = 기본 타격량 × 타격 배율 × 전체 생산 배율 × 환생 배율
최종 주문 보상    = 기본 주문 보상 × 주문 보상 배율
최종 오프라인 보상 = 기본 오프라인 보상 × 오프라인 효율 배율
```

- 같은 효과를 여러 곳에서 획득해도 계산 순서를 바꾸지 않습니다.
- 확률 효과는 별도 이벤트로 계산하며, 발동 확률에는 필요 시 상한을 두되 생산량 자체에는 임의의 낮은 하드 캡을 두지 않습니다.
- 각 계층의 실제 값은 데이터 설정으로 관리해 밸런스 패치가 가능하게 합니다.
- **검증 필요**: 명인의 인장 영구 강화는 단계당 최대 +100%(20단계×5%)까지 성장하는 반면 유물은 개별 효과가 최대 +3% 수준입니다. 하드 캡이 없는 설계이므로 두 시스템의 체감 비중이 크게 벌어질 수 있어, 실제 곡선 시뮬레이션에서 유물이 여전히 "있으면 좋은" 수준으로 느껴지는지 확인합니다.

### 6.4 환생 재설계

"환생마다 전체 생산 +10%" 같은 고정 배율 대신, 환생 전용 재화 **명인의 인장**을 도입합니다.

**환생 시 초기화**: 현재 잉걸불 / 잉걸불로 구매한 일반 업그레이드 / 진행 중인 일반 주문 / 현재 세션용 임시 버프

**환생 후 유지**: 평생 누적 잉걸불 / 업적과 도감 기록 / 명인의 인장과 영구 능력 / 해금한 외형 요소 / 설정과 접근성 옵션 / (V1.1+) 유물과 룬 파편

**명인의 인장 획득 공식**
```text
획득 인장 = floor((이번 생애 누적 잉걸불 ÷ 환생 기준값)^0.5)
```
`환생 기준값`은 첫 환생에서 1~3개 인장을 얻도록 시뮬레이션으로 결정합니다. 환생 화면에서 초기화 항목, 유지 항목, 예상 인장, 강화 후 예상 생산량을 미리 보여주며, 예상 인장이 0개일 때는 환생할 수 없습니다.

**명인의 인장 영구 강화 예시**

| 강화 | 효과 | 최대 단계 예시 |
|---|---|---:|
| 숙련된 손길 | 타격 생산량 +5%/단계 | 20 |
| 자동 풀무 | 자동 생산량 +5%/단계 | 20 |
| 밤샘 작업 | 오프라인 효율 +3%/단계 | 10 |
| 왕실 계약 | 주문 보상 +4%/단계 | 10 |
| 유물 감정 | (V1.1 이후) 유물 조각 획득량 증가 | 10 |

환생 강화는 직접 타격형·방치형·주문형 등 원하는 방향으로 자유롭게 투자할 수 있게 구성합니다 (하나만 고르는 배타적 선택이 아님).

### 6.5 경제 소진 장치

**V1.0**: 업그레이드 구매 / 주문 제작 비용 / 명인의 인장 소비(영구 강화 구매)
**V1.1부터**: 유물 뽑기와 외형 해금을 추가 소진처로 사용

### 6.6 큰 숫자 표시

- 내부 값과 화면 표기를 분리합니다. 화면은 `1.25K`, `3.40M`, `7.82B`처럼 표시합니다.
- 설정에서 한국식 단위와 영문 축약 단위를 선택할 수 있도록 확장 가능하게 설계합니다.
- 비교와 저장은 축약 문자열이 아니라 원본 큰 수 값으로 수행합니다.

## 7. 오프라인 보상 설계

백그라운드 타이머를 계속 실행하는 방식이 아니라, **마지막 저장 시각과 복귀 시각의 차이**로 계산합니다.

```text
오프라인 시간 = min(현재 시각 - 마지막 정상 저장 시각, 최대 오프라인 시간)
오프라인 보상 = 저장 시점의 초당 자동 생산량 × 오프라인 시간 × 오프라인 효율
```

**V1.0 기본값**: 최대 오프라인 시간 8시간, 기본 오프라인 효율 70% (환생 영구 강화로 효율 상승 가능). 복귀 화면에서 경과 시간·기본 보상·적용 배율을 구분해서 표시합니다.

**생명주기 처리**: 백그라운드 전환 시 즉시 저장, 활성화 시 시간 차이 계산, 강제 종료 대비 주기적 자동 저장 유지, `offlineClaimId` 또는 마지막 지급 시각 저장으로 중복 지급 방지.

**기기 시간 변경 정책**

| 상황 | 처리 |
|---|---|
| 현재 시각이 마지막 저장 시각보다 이전 | 오프라인 보상 0, 시간 이상 상태 기록 |
| 비정상적으로 긴 시간 차이 | 최대 8시간으로 제한 |
| 짧은 시간 안에 반복적인 시간 변경 감지 | 보상 제한 및 분석 이벤트 기록 |

## 8. 저장 및 데이터 복구 설계

클릭커 게임은 저장 손실이 가장 치명적인 문제이므로 저장 시스템을 독립 기능으로 취급합니다.

### 8.1 저장 데이터 기본 구조

```ts
interface SaveData {
  saveVersion: number;
  profile: { createdAt: string; lastActiveAt: string; locale: string };
  economy: { ember: string; lifetimeEmber: string; runLifetimeEmber: string; clickCount: string };
  upgrades: Record<string, number>;
  prestige: { count: number; masterSeals: number; permanentSkills: Record<string, number> };
  orders: OrderSaveState;
  achievements: Record<string, AchievementState>;
  unlocks: string[];
  settings: GameSettings;
  offline: { lastCalculatedAt: string; lastClaimId?: string };
  integrity: { savedAt: string; checksum?: string };
}
```

### 8.2 저장 시점

15~30초 주기 자동 저장 / 업그레이드 구매 직후 / 주문 시작·완료·보상 수령 직후 / 업적 보상 수령 직후 / 환생 확인 직전과 완료 직후 / 앱 백그라운드 진입 시 / 설정 변경 시

### 8.3 이중 백업

`primarySave`(최신 저장본), `backupSave`(직전 정상 저장본). 저장 순서: ① 기존 primarySave 검증 → ② 정상이면 backupSave로 복사 → ③ 새 데이터를 임시 키에 기록 → ④ 다시 읽어 파싱·필드 검증 → ⑤ 정상일 때만 primarySave로 교체

### 8.4 데이터 검증

JSON 파싱 성공 여부, 필수 필드 존재 여부, 음수일 수 없는 값의 범위, 업그레이드 수량·최대 레벨, 날짜 형식·비정상 시간 차이, 저장 버전 호환성, 큰 수 문자열 형식. 검증 실패 시 직전 백업을 복원하고 `save_recovered` 분석 이벤트를 남깁니다.

### 8.5 저장 마이그레이션

모든 저장 데이터에 `saveVersion`을 두고 `v1 → v2 → v3` 순서로 한 단계씩 실행합니다. 마이그레이션 전 원본은 별도 보관하며, 실패 시 앱을 종료시키지 않고 백업 복구 또는 안전 초기화 선택지를 제공합니다. 마이그레이션 함수는 단위 테스트를 작성합니다.

### 8.6 초기화 및 복구 UX

설정 화면에서 게임 데이터 초기화(두 번 확인 + 확인 문구 입력), 저장 복구 발생 시 복구된 시점 안내를 제공합니다. 데이터 내보내기/복구 코드는 V1.2에서 검토합니다.

### 8.7 클라우드 저장 (V1.2)

- 로컬 저장이 항상 기본 동작을 유지하며, 클라우드와 로컬이 충돌하면 플레이 시간·저장 시각·평생 누적값을 비교해 사용자가 선택하게 합니다. 단순히 더 큰 잉걸불 값만 기준으로 병합하지 않습니다.
- 구매 내역은 로컬 저장값을 소유권의 유일한 증거로 사용하지 않고, 10.5의 구매 검증·복원 절차를 항상 함께 거칩니다. 기기 변경처럼 클라우드 복원과 구매 복원이 동시에 걸리는 상황에서는 **클라우드 저장 복원 → 구매 내역 서버 검증·복원 → 최종 병합 확인 화면** 순서로 처리해, 사용자가 병합 결과를 확인하기 전에 결제 상태가 먼저 확정되지 않게 합니다.

## 9. 유물 시스템 (V1.1)

유물은 V1.0 핵심 출시 후 리텐션 업데이트에서 추가합니다.

### 9.1 목적

후반 잉걸불 소진처 제공 / 수집과 도감 완성 동기 제공 / 플레이 스타일을 조금씩 변화시키는 패시브 효과 제공

### 9.2 뽑기 비용

보유 잉걸불을 기준으로 가격을 조정하면 재화를 먼저 소비해 가격을 낮추는 문제가 생기므로 사용하지 않습니다. 아래 두 방식 중 스프레드시트 테스트에서 악용 가능성과 체감 가격이 더 안정적인 쪽을 선택합니다.

```text
방식 A: 뽑기 비용 = 대장간 티어별 기본 비용 × 1.03^누적 뽑기 횟수
방식 B: 뽑기 비용 = 최고 기록 초당 생산량 × 120 × 1.03^누적 뽑기 횟수
```

### 9.3 확률과 개별 유물 확률

뽑기 풀은 일반 8종·희귀 5종·전설 2종으로 구성합니다.

| 등급 | 등급 확률 | 개별 확률(균등 분배 시) |
|---|---:|---:|
| 일반 8종 | 70% | 각 8.75% |
| 희귀 5종 | 25% | 각 5.00% |
| 전설 2종 | 5% | 각 2.50% |

등급별 확률뿐 아니라 개별 유물 확률을 게임 내에 표시하고, 실제 확률표는 앱 버전과 함께 관리하며 변경 이력을 남깁니다.

### 9.4 중복 보상과 확정 획득

중복 유물은 조각으로 전환합니다. 무료 재뽑기는 결과를 보장하지 않으므로 "천장"으로 부르지 않고, 대신 조각으로 원하는 미보유 유물을 직접 제작할 수 있게 합니다.

| 등급 | 중복 시 조각 | 선택 제작 필요 조각(예시) |
|---|---:|---:|
| 일반 | 1개 | 10개 |
| 희귀 | 3개 | 30개 |
| 전설 | 8개 | 80개 |

수치는 테스트 후 조정합니다.

  독립 탭으로 분리했습니다. 사유와 경위는 `README.md`의 "계획서 불일치" 절에 있습니다.)
- 환생은 대장간 또는 기록 화면에서 별도 모달로 진입시켜 실수로 인한 초기화를 방지합니다.
- 탭에 미완성 기능을 미리 노출하지 않습니다.
- 업적 화면은 **수령 대기 → 진행 중 → 달성 완료** 세 묶음을 모두 펼쳐 둡니다. 항목마다
  이름·진행도와 함께 달성 조건 문구를 작은 글씨로 붙입니다. 이름과 숫자만으로는 그 수가
  무엇을 세는 것인지 읽히지 않기 때문입니다.
- V1.1에서 기록 화면 안에 도감과 유물 뽑기·보관함을 추가합니다.
- V1.2에서 랭킹을 독립 탭으로 추가할지는 사용 데이터를 보고 결정합니다.

### 12.3 튜토리얼 흐름

```text
1. 모루 5회 타격 → 2. 첫 업그레이드 구매 → 3. 자동 생산 확인
→ 4. 첫 주문 시작 → 5. 첫 주문 보상 수령 → 6. 기록 화면과 저장 안내
```

강제 설명 팝업을 연속으로 띄우기보다 실제 UI를 강조하며 한 단계씩 진행합니다.

### 12.4 환생 안전장치

예상 보상과 초기화 항목을 명확히 표시하고, 첫 환생은 추가 안내 화면을 제공합니다. 확인 문구 입력 등 강한 확인 절차는 첫 환생에서만 고려하며, 환생 실행 직전 자동 저장과 백업을 생성합니다.

## 13. 사운드·햅틱·연출

### 13.1 효과음

| 상황 | 사운드 |
|---|---|
| 모루 타격 | 금속 타격음, 타격력과 열기에 따라 피치 변화 |
| 업그레이드 구매 | 짧은 금속 울림과 재화 소비음 |
| 주문 완료 | 무기 완성·납품을 느끼게 하는 짧은 팡파르 |
| 업적 달성 | 밝은 팡파르 |
| 환생 | 불꽃이 크게 타오르는 사운드와 공간감 있는 전환음 |
| 오프라인 보상 | 잉걸불이 쌓이는 소리 |
| 일반 버튼 | 반복 피로가 적은 절제된 클릭음 |

### 13.2 BGM

화로 티어에 따라 3~4단계로 악기와 웅장함을 확장하며 즉시 끊기보다 크로스페이드로 전환합니다. SFX·BGM 음량을 각각 조절할 수 있게 하고, 앱이 백그라운드로 전환되면 음악을 일시 중지합니다.

### 13.3 햅틱

일반 타격(약한 햅틱) / 완벽 타격·치명 효과(중간 햅틱) / 업그레이드·주문 완료(짧은 성공 햅틱) / 환생(강한 햅틱 1회). 설정에서 완전히 끌 수 있게 합니다.

### 13.4 성능 원칙

타격할 때마다 React 전체 화면을 다시 렌더링하지 않습니다. 파티클 수는 기기 성능·설정에 따라 줄일 수 있게 하고, 숫자 애니메이션·사운드는 동시에 과도하게 생성되지 않도록 풀링 또는 제한을 둡니다.

## 14. 접근성

- **색상 대비**: 화로 색상만으로 상태를 전달하지 않고 아이콘·형태·명도 차이를 함께 사용
- **폰트 크기**: 시스템 글자 크기 또는 앱 내 크기 설정 지원
- **터치 영역**: iOS 최소 44×44pt, Android는 Material 가이드라인 기준 최소 48×48dp를 각각 적용 (플랫폼별 기준이 다르므로 공용 컴포넌트에서 더 큰 쪽인 48dp 상당을 기본값으로 통일하는 것을 권장)
- **모션 감소**: 화면 흔들림, 반짝임, 파티클, 숫자 튀김 감소
- **스크린 리더**: 모루, 재화, 생산량, 구매 버튼에 의미 있는 레이블 제공
- **햅틱 대체**: 햅틱 없이도 시각·청각 피드백 제공
- **한 손 조작**: 핵심 버튼을 화면 하단 또는 엄지 접근 영역에 배치
- **빠른 반복 입력**: 모루 타격이 보조 기술 사용자의 입력을 불필요하게 차단하지 않게 설계
- **색각 모드**: 필요 시 화로 티어 강조 패턴 추가

**확률형 콘텐츠 권장 문구**: "유물 뽑기가 유료 재화 또는 유료 상품과 직접·간접적으로 연결되는 경우 확률형 아이템 표시 의무 대상이 될 수 있다. 출시 국가, 사업자 규모, 재화 전환 구조가 확정된 뒤 법률 검토를 진행한다. 의무 여부와 별개로 이용자 신뢰를 위해 개별 유물 확률을 게임 내에 공개한다."

**스토어 심사 노트 준비**: 핵심 게임 루프 설명, 환생 조건과 초기화·유지 항목, 유물 확률 화면 위치, 광고 표시 조건, IAP 상품별 기능, 테스트 계정과 숨겨진 기능 해금 방법, 계정·데이터 삭제 경로, 심사자가 첫 환생·후반 기능을 빠르게 확인할 수 있는 테스트 방법

**WebView 포장 금지**: 기존 React 웹페이지를 단순 WebView로 감싸지 않고 React Native 화면과 네이티브 UX로 실제 전환합니다.

## 24. 최종 권장 결정

1. V1.0은 타격, 업그레이드, 주문 제작, 오프라인 보상, 업적, 첫 환생, 저장·복구에 집중합니다.
2. 유물, 룬 파편 판매, 랭킹, 시즌 패스는 출시 후로 이동합니다.
3. 환생은 고정 +10% 대신 명인의 인장과 영구 강화 트리로 설계합니다.
4. 오프라인 보상은 백그라운드 타이머가 아니라 마지막 저장 시각과 복귀 시각의 차이로 계산합니다.
5. 저장 시스템은 `saveVersion`, 자동 저장, 이중 백업, 검증, 마이그레이션을 기본 요구사항으로 둡니다.
6. 유물 도감 완성도는 뽑기 풀 15종만 기준으로 계산하며, 조각으로 원하는 미보유 유물을 확정 제작할 수 있게 합니다.
7. 강제 전면 광고는 사용하지 않고, V1.1부터 선택형 보상 광고만 검토합니다.
8. 랭킹은 결제·유물·영구 강화가 비활성화된 동일 조건 챌린지를 중심으로 설계합니다.
9. 스토어 계정과 테스트 준비를 개발 후반이 아니라 Phase 0부터 병행합니다.
10. 실제 개발은 게임 엔진 → 저장·복구 → 화면 → 네이티브 UX → 수익화 순서로 진행합니다.
11. 보너스 스택 규칙(6.3)은 생산·타격뿐 아니라 주문 보상·오프라인 효율까지 모두 포괄하는 공용 공식으로 관리합니다.
12. 접근성 터치 영역은 iOS 44pt·Android 48dp를 각각 반영하고, 공용 컴포넌트는 더 큰 기준에 맞춥니다.
